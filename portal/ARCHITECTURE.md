## עקרון המודולריות (§2.1) — איך הוא ממומש בפועל

זו ההחלטה המרכזית בקוד. שני מנגנונים:

### 1. `MODULES` — רישום מודולים

```js
const MODULES = {
  rehab:    { pricing:'package',      intake:'intake_rehab',    active:true  },
  wellness: { pricing:'subscription', intake:'intake_wellness',
              trialFirst:true,        active:false }
};
```

הוספת מודול עתידי (§12 — שיפור ביצועים, מניעת נפילות, B2B) = **הוספת רשומה**.
שדה `pricing` מיישם ישירות את §13 — package מול subscription.
`trialFirst` מיישם את §213 — לקוח וולנס חדש רואה רק "התנסות", המנוי מוצג רק אחרי הטיפול הראשון.

### 2. `FORMS` — מנוע שאלון מונחה-דאטה

זו הדרישה המפורשת ב-§194: *"מנוע שאלון דינמי גנרי, לא שאלון מקודד קשיח לתחום אחד"*.

שאלון = סכמה. הרנדרר לא יודע דבר על תוכן קליני:

```js
{ id:'nprs_now', type:'scale', instrument:'NPRS', req:true,
  lo:'ללא כאב', hi:'הכאב החמור ביותר' }
```

סוגי שדה נתמכים: `text · tel · date · select · radio · checks · scale · textarea · psfs`
תמיכה בשדות מותנים דרך `showIf` (למשל: "לאן מקרין" מופיע רק אם נבחר "כן").

**המשמעות:** שאלון הוולנס העתידי הוא אובייקט חדש ב-`FORMS`. אפס שינוי בקוד.

### הפרדת Core / Module בשכבת הנתונים

```
CORE     users · appointments · audit_log · מנוע השאלון · הרשאות
MODULE   סכמת שאלון · ספריית תוכן · מסלול תמחור
```

מבנה ה-store משקף כבר עכשיו את סכמת ה-DB העתידית, כדי שהמעבר לשרת לא ידרוש שינוי מבני.

## שאלוני התפקוד

**NPRS** (§55) — סולם 0–10, שתי מדידות: כאב עכשיו + החמור בשבוע האחרון.
צבע הסולם משתנה עם הערך (ירוק→אדום).

**PSFS** (§55) — עד 3 פעולות שהלקוח בוחר, כל אחת מדורגת 0–10.
כאן הסולם **הפוך** (0 = לא מסוגל, 10 = כמו לפני הבעיה) — והצבע מתהפך בהתאם.
זה מדד הבסיס להשוואה בהערכה החוזרת (§62).

**DASH** — לא נכלל בשלב 1. שאלון ארוך וספציפי לגפה עליונה; מתאים להוספה כמודול שאלון נפרד כשיידרש.

## דרישות לא-פונקציונליות

**§6.2 עברית ו-RTL** — `dir="rtl"` ברמת המסמך, `inline-start/end` בכל מקום שיש כיווניות.

**§6.4 נגישות לאוכלוסייה מבוגרת** — בסיס 17px (לא 14/16), יעדי מגע ≥44px, `:focus-visible` נראה בכל אלמנט אינטראקטיבי, `prefers-reduced-motion` מכובד, ניווט שטוח ללא תפריטים מקוננים.

**§6.3 שקיפות מול המשתמש** — הרכיב `.ai-flag` בנוי ומוכן, אך **אינו בשימוש בשלב 1** כי אין פלט AI. הוא נמצא שם כדי שכשיגיע שלב 2 התיוג יהיה כבר חלק מהמערכת ולא תוספת מאוחרת.

**§5.7 תיעוד** — כל אירוע מהותי נרשם ל-`S.log` ומוצג ללקוח ב"יומן פעילות". בשרת זה יהפוך ל-audit log בלתי-ניתן-לעריכה.

**§6.1 זכויות במידע** — "הורדת עותק" ו"מחיקת כל המידע" בפרופיל, כמימוש זכות העיון והמחיקה.

## מה חייב להשתנות לפני production

האזהרה מוצגת גם בממשק עצמו, בתחתית מסך הפרופיל:

| נושא | מצב נוכחי | נדרש |
|---|---|---|
| אחסון | `localStorage` בדפדפן | שרת + DB, הצפנה at rest |
| תעבורה | — | HTTPS, הצפנה in transit (§6.1) |
| אימות | דמו — כל קלט מתקבל | אימות אמיתי + 2FA (§5.1) |
| הרשאות | לקוח בלבד | הפרדת לקוח/מטפל (§5.1) |
| הסכמה מדעת | טקסט placeholder | נוסח מאושר עו"ד (§7) |
| ביטוח | — | אישור מבטח לפני השקה (§7) |

**חוסמים לפי §10:** אישור משפטי לתחום עיסוק חוסם את שלב 2 ואילך. כיסוי ביטוחי חוסם השקה ללקוחות אמיתיים.

## מה לא נבנה בכוונה

**פאנל מטפל.** §3 מגדיר את גיל כמשתמש נפרד עם הרשאות שונות. זה מסך אחר לגמרי (רשימת לקוחות, אישור/תיקון תוצרי AI, בניית תוכנית) ומצדיק בנייה נפרדת — במיוחד כי בשלב 2 הוא הופך למקום שבו מתבצע אישור פלט ה-AI, שהוא נקודת הבקרה הקלינית של כל המערכת.

**תשלומים.** §2.1 מגדיר אותם כחלק מהליבה, אך §9 לא כולל אותם בשלב 1. מבנה התמחור כבר מיוצג ב-`MODULES` כדי שהחיבור יהיה נקודתי.

## שאלות פתוחות (§11) — רלוונטיות לבנייה

1. **פלטפורמת HEP** — משפיע על מבנה תוכנית התרגילים בשלב 3. עד שתתקבל החלטה (§9.1) לא כדאי לבנות סכמת תרגילים.
2. **מרווח הערכה חוזרת** — שבועיים או חודש. משפיע על מנגנון התזמון בשלב 4.
3. **תורי וידאו** — מומש בממשק כאופציה ("שיחת וידאו להבהרות"), עם הבהרה שהטיפול עצמו פרונטלי. אם ההחלטה תהיה לא לכלול — זו הסרה של שורה אחת.
